# 拾贝 & 串珠：全天录音的场景理解与知识沉淀（设计稿）

状态：设计稿，未实现。日期：2026-11-08。

## 1. 要解决的问题

用户全天开着录音，录音笔按时长或静音切成多个长文件。一个文件里可能先后出现通勤、闲聊、加微信、听课、开会。现有流水线是 `转录 → organize.ts 固定 schema 归类`：一个文件只有一个标题和一个分类，也不认识人、不理解场景、不积累知识。

两类核心价值：

1. **个人 CRM**：谁、在什么时候、在什么场合和我交换了联系方式，聊了什么，约了什么。
2. **知识体系**：长课、讲座、讨论里出现的实体、关系、概念解释、方法论、灵感和待办，持续沉淀进一个可长期生长的 Markdown 知识库。

## 2. 两个 bot 的职责划分

| | 拾贝（自下而上） | 串珠（自上而下） |
| --- | --- | --- |
| 比喻 | 在一天录音的沙滩上捡有意思的贝壳 | 把贝壳按图样串进项链 |
| 输入 | 转录全文与分段（含说话人标签）、录音时间、日历、已有人物库 | 拾贝切好的场景、选定的模板、现有知识库索引 |
| 职责 | 切分场景；判断场景类型并匹配模板；发现人物与"交换联系方式"时刻；遇到没有合适模板的场景时，先停下来设计一份新模板提案 | 按模板逐个字段抽取；产出实体、关系、概念解释、方法论、待办、灵感；生成知识库写入提案；执行用户采纳的写入 |
| 不负责 | 不写知识库正文 | 不决定场景边界，也不发明模板（只能对模板提修订建议） |
| 产物 | 场景、人物线索、模板提案 | 抽取结果、知识库变更提案 |

职责边界：**拾贝决定"这是什么、该用什么模板"，串珠决定"按模板该记下什么、记到哪里"**。串珠抽取时如果发现模板反复缺字段，只把这个信号回报给拾贝，由拾贝发起模板修订提案。

两个 bot 都**全自动运行**。但凡会改变长期资产的结果（新人物、人物合并、新模板、模板修订、知识库写入），一律进入"待确认收件箱"，用户可以一键采纳、修改或驳回。

## 3. 流水线

```
录音文件 ─转录(开启说话人分离)─▶ transcript + segments(speaker)
   │
   ▼  拾贝·切场景（按天聚合，可跨文件）
scenes[]: 起止时间 / 来源分段 / 场景类型 / 置信度 / 模板
   │        ├─ 匹配到模板 ─────────────┐
   │        └─ 没匹配 → 模板提案 ▶ 收件箱  │(采纳后回流)
   ▼  拾贝·认人                         ▼
人物线索 / 联系方式交换时刻 ▶ 收件箱     串珠·按模板抽取
                                       │
                                       ▼
                         extraction（结构化字段 + 实体/关系/概念/待办/灵感）
                                       │
                                       ▼  串珠·知识库写入提案
                              vault diff ▶ 收件箱 ▶ 采纳后写入 Markdown
   ▼  全部场景处理完
拾贝 + 串珠 联合生成「今日简报」
```

要点：

- **场景按天切，不按文件切**。拾贝把同一天的录音按 `recorded_at + 分段偏移` 排成一条时间线，场景可以跨两个文件的边界（例如课程刚好被切成两个文件）。
- 切分分两步：先用规则粗切（长静音、说话人集合突变、日历事件边界、文件边界），再让 LLM 在粗切边界附近判断合并还是拆分，并给出场景摘要与类型。超长文本按窗口滑动处理，相邻窗口保留重叠区，避免把场景切碎。
- 现有的 `organize.ts` 文件级归类保留，作为录音库的列表标题和分类。新的场景层是另一层视图，两者互不覆盖。
- 每一步都是可重试的 job，复用 `job_runs`。场景、抽取结果、提案都记录来源版本（transcript id、模板版本、引擎），转录被修改后，下游结果标记为过期，不静默覆盖。

## 4. 场景模板

模板是一份声明式定义：判定场景的线索（何时该用这份模板）加上要抽取的字段。拾贝负责匹配模板，串珠负责照着字段抽取。

```yaml
slug: lecture
name: 听课 / 讲座
version: 3
when: 单一主讲人长时间输出，出现"今天讲""第几点""大家看"等授课语气
fields:
  - key: speaker        # 讲者
    type: person_ref
  - key: concepts       # 核心概念及解释
    type: list<concept>  # {name, explanation, quote, ts}
  - key: methods        # 方法论 / 步骤
    type: list<method>   # {name, steps[], when_to_use}
  - key: cases          # 案例
    type: list<text>
  - key: resources      # 书单 / 工具 / 链接
    type: list<entity>
  - key: experiments    # 可以尝试的灵感
    type: list<idea>
  - key: todos
    type: list<todo>
vault:                  # 采纳后写到哪里
  source_page: sources/{date}-{title}.md
  concepts: concepts/
  methods: methods/
  ideas: ideas/
```

第一版内置四份模板：

| slug | 场景 | 关键字段 |
| --- | --- | --- |
| `social` | 结识新朋友 / 社交 | 对方身份、公司职位、共同话题、联系方式交换时刻、后续约定 |
| `lecture` | 听课 / 讲座 | 讲者、核心概念及解释、方法论步骤、案例、书单/工具、可尝试的实验 |
| `meeting` | 会议 / 商务沟通 | 参与人、决策、分歧、待办（责任人、截止时间） |
| `musing` | 自言自语 / 灵感随记 | 灵感、待办、情绪与反思 |

另有一个兜底类型 `ambient`（通勤、背景噪声、无实质内容）：只保留转录，不做抽取，在简报里也不出现。

**拾贝怎么设计新模板**：场景与所有模板的匹配置信度都低于阈值时，拾贝不硬套模板，而是先回答三个问题：这是什么场景？在这个场景下，用户以后最可能想找回哪些信息？哪些字段和现有模板重叠？然后生成一份模板草稿和一个用当前场景试抽的样例，一起放进收件箱。用户采纳后，这份模板对当天的场景回溯生效，以后自动套用。用户驳回时，场景退回到最接近的已有模板。同一类场景积累到 N 次（默认 3 次）才发起提案，单次出现的怪场景先用最接近的模板加通用字段处理，避免模板泛滥。

模板存在数据库里，并按版本管理；同时导出一份到知识库的 `_templates/` 目录，方便用户直接编辑 YAML。工作台检测到文件变化后，会生成一个新版本。

## 5. 人物识别（个人 CRM）

### 5.1 证据源（可插拔，接入了就用）

| 证据源 | 第一版 | 提供什么 |
| --- | --- | --- |
| 录音文本 | ✅ | 自我介绍、称呼、公司职位、"我扫你""加个微信""我把名片发你"等**联系方式交换时刻** |
| 会话内说话人分离 | ✅ | Host ASR 的 `speakerId`。只在一个 ASR 会话内有效；现有转录每 300 秒开一个新会话（`src/server/transcribe.ts:50`），所以同一个文件里跨块的编号也不保证一致（见 §12） |
| 日历参会人 | ✅ | `calendar_events.attendees`，按时间与场景重叠关联 |
| 微信新好友 | 接口预留 | 本期不接入，留好 `contact_events` 导入接口 |

本期**不做跨录音声纹**。跨天、跨文件认出同一个人，只靠姓名、称呼、公司、话题、日历这类文本线索，再由用户在收件箱里确认合并。

每条证据记成一条 `person_evidence`，包含来源、时间点、场景、原文引用和置信度。人物结论由多条证据汇总而来，不依赖单一来源。

### 5.2 "加微信"时刻

拾贝在 `social` 和 `meeting` 场景里专门找**联系方式交换事件**，记录时间点（精确到分段）、说话人、上下文原文和对方的已知特征（称呼、公司、话题）。这个事件是 CRM 的锚点：以后接入微信新好友记录时，按 ±10 分钟窗口和事件对齐，就能把微信昵称挂到这个人身上。

### 5.3 人物生命周期

1. 拾贝产出**人物线索**：场景里与用户有实际对话的说话人，或被明确提到姓名的人。
2. 拾贝与已有人物比对（姓名、称呼、公司、话题、日历参会人），给出"新人物"或"可能是某某"的提案，进入收件箱。
3. 用户采纳后建立或合并 `people` 记录，并生成 `people/<姓名>.md`。
4. 以后每次出现，串珠都往这个人的页面追加一条"互动记录"：时间、场景、聊了什么、约了什么，并附双链。

人物合并永远需要用户确认，合并后可以拆回。

## 6. Markdown 知识库

默认位置 `~/memo/knowledge/`，可在设置里修改。首次启用时生成骨架：

```
knowledge/
├── people/        一人一页：身份、认识经过、互动时间线、约定
├── concepts/      一个概念一页：解释（可来自多个来源）、相关概念、出处
├── entities/      组织、产品、书、工具、地点
├── methods/       方法论：步骤、适用场景、出处、我的实践记录
├── ideas/         灵感 / 想试的实验，带状态（待试 / 试过 / 放弃）
├── sources/       每个场景一页（一节课、一次会、一次聚会），汇总本次抽取并链接到上面各页
├── todos.md       待办汇总（也可以按月拆分）
├── daily/         每日简报存档
└── _templates/    场景模板 YAML
```

写入规则：

- 页面用 `[[双链]]` 互相关联，能在 Obsidian 中直接打开。frontmatter 记录 `om_id`、`om_type`、`aliases` 和 `sources`，用于幂等更新与改名识别。
- **工作台只改自己管理的区块**：用 `<!-- om:begin key -->…<!-- om:end key -->` 包住机器生成的段落，区块之外是用户自由编辑区，工作台从不改动。用户改了区块内部的内容时，工作台检测到哈希不一致，就把这次写入转成冲突提案，不覆盖用户的修改。
- 概念被多次提到时**累积解释，不覆盖**：每条解释带出处（场景链接、时间戳原文），由串珠在收件箱里提议是否合并成一段综合解释。
- 所有写入都先落到 `.workbench/vault-staging/<proposalId>/`，生成文件级 diff 放进收件箱，用户采纳后才原子替换到知识库。写入后逐个回读校验文件是否存在、`om_id` 是否匹配、区块哈希是否正确。
- SQLite 中保留实体、关系和概念的索引表，用于工作台内搜索和去重；Markdown 是最终交付物。索引可以由知识库重建。

## 7. 待确认收件箱

| 提案类型 | 发起者 | 采纳后 |
| --- | --- | --- |
| `person.new` | 拾贝 | 新建人物与人物页 |
| `person.merge` | 拾贝 | 合并两个人物（可拆回） |
| `template.new` / `template.revise` | 拾贝 | 新模板或新版本生效，可选回溯当天场景 |
| `vault.write` | 串珠 | 把 staging diff 写入知识库（按场景打包，一张卡一次写入） |
| `concept.consolidate` | 串珠 | 合并某个概念的多条解释 |
| `vault.conflict` | 串珠 | 用户在三方 diff 中选择保留哪一方 |

交互要求：

- 每张卡片都用 bot 的口吻写一句人话，旁边是结构化内容和原文证据（可以点击跳转到录音的对应时间点播放）。
- 三个主操作：**采纳**、**改一下再采纳**（就地编辑字段）、**驳回**（可选填原因，作为反馈喂回 bot 的提示词）。
- 支持按类型批量采纳。驳回的提案不会以同样的内容再次出现。
- 待办和灵感本身不需要确认就会出现在简报和工作台里，只有写进知识库这一步需要确认。

## 9. 执行引擎：内置或本地 CLI agent

### 9.1 可选择的环节

每个环节都可以单独选择引擎，**默认全部使用内置**：

| 环节 | 所属 bot | 默认 | 说明 |
| --- | --- | --- | --- |
| 场景切分 | 拾贝 | 内置 LLM | 结构化输出 |
| 模板匹配 | 拾贝 | 内置 LLM | 结构化输出 |
| 人物识别与比对 | 拾贝 | 内置 LLM | 需要读取人物库摘要 |
| 新模板设计 | 拾贝 | 内置 LLM | 适合换成 CLI：需要参考现有模板和知识库 |
| 按模板抽取 | 串珠 | 内置 LLM | 结构化输出 |
| 知识库写入提案 | 串珠 | 内置 LLM | 适合换成 CLI：要读写多个页面、做去重与双链 |
| 概念合并 | 串珠 | 内置 LLM | 同上 |
| 每日简报 | 共同 | 内置 LLM | |

可选引擎：`内置 LLM`（Host `llm.generateObject`）、`Floatboat Agent`（Host `agent`）、`Claude Code`、`Codex`、`Hermes`、`pi`。

### 9.2 检测

设置页新增"执行引擎"卡片：按"用户配置的路径 → PATH → 常见安装位置"的顺序探测 `claude`、`codex`、`hermes`、`pi`，运行版本命令，显示路径、版本和是否可用。用户可以手动指定可执行文件路径。每种 CLI 有一个适配器，声明非交互调用参数、工作目录参数、允许写入的目录参数和输出格式。复用现有 `tools.ts` 的发现逻辑。

### 9.3 执行契约：先指定位置，事后必须确认文件存在

```
.workbench/agent-runs/<runId>/
├── task.md          任务说明 + 输出契约（文件路径、JSON Schema）
├── input/           本次用到的转录片段、模板、知识库相关页面副本
├── output/          CLI 唯一允许写入的位置
│   └── result.json  （或者 vault-staging 下的若干 .md）
└── run.json         引擎、参数、退出码、耗时、校验结果
```

1. **执行前**：工作台创建 run 目录，在 `task.md` 中写明必须产出的文件的绝对路径和 Schema，以 `output/` 为唯一可写目录（CLI 支持沙箱参数时一并传入），cwd 设为 run 目录。
2. **执行**：非交互方式调用，设置超时，记录 stdout/stderr。
3. **执行后校验**（不看退出码，只看产物）：期望的文件是否都存在、能否解析、是否符合 Schema；知识库类任务还要校验 `om_id` 与区块标记是否完整，以及是否越界写入了 `output/` 以外的位置（对比 run 前后的文件快照）。
4. **修复**：校验失败时，把具体失败项（缺哪个文件、哪个字段不合 Schema）写进 `repair.md`，用同一个引擎在同一目录重跑一次。最多修复 2 次，仍然失败就把这一步标记为失败并退回内置引擎重试（可在设置中关闭这次回退），并在执行记录中如实展示原因。
5. CLI 永远不直接写入真实知识库。它的产物都进入 staging，再走收件箱。

## 10. 数据模型（新迁移从 `0008` 起，按分期拆分；`0007` 已用于设备服务）

P1 只建 `templates`、`scenes`、`extractions` 三张表（`0008_scenes.sql`），其余表在对应分期再加迁移。

| 表 | 关键字段 |
| --- | --- |

## 12. 待定项

1. ~~跨录音声纹~~：已决定本期不做（2026-11-08）。
2. **超长录音：文档无法确定，需要实测**。
   - 查到的情况：豆包大模型流式识别的说话人分离参数是 `enable_speaker_info`，需配合 `show_utterances`，结果里每句带 `speaker_id` 和毫秒时间戳。产品页写支持最长 2 小时的长音频，但没有说明是否适用于流式接口。没查到单个流式会话的时长上限，也没查到 `speaker_id` 是否跨会话稳定。官方文档页面这次没能直接抓取，以上来自检索摘要，未逐字核对原文。
   - 代码里的已知事实：Host ASR 的契约（`sdk/asr-contracts.d.mts`）没有写明后端是豆包，也没有时长参数。现有转录已经实测到长会话会中途 `ASR_UPSTREAM_FAILED`，所以按 300 秒分块，失败时续传（`src/server/transcribe.ts:50`）。也就是说，3 小时的课能转出来，但每 5 分钟换一个会话，**`speakerId` 很可能每块重新编号**，讲者和提问者在块之间会对不上。
   - 实测计划（P0，P1 之前做）：用一段 ≥1 小时、≥3 人的真实录音，经 `verify-openminutes` 复用 Floatboat Host 跑三组分块时长（300 / 900 / 1800 秒），记录：上游中断次数和位置；相邻块的 `speakerId` 是否延续；转录总耗时。再把同一份转录送 Host LLM，记录单次可接受的最大输入长度和失败形态。
   - 按结果决定：如果长会话稳定、编号延续，就加大分块；否则保留 300 秒分块，由拾贝在块边界用重叠区原文和称呼把相邻块的说话人对齐，对齐不确定的标为未知，不硬合。LLM 抽取窗口按实测上限的一半设置，相邻窗口保留重叠。
3. **转录时默认开启说话人分离**：当前设置中已有开关（默认启用）。场景切分和认人都依赖它，关闭后只能退化为纯文本线索。

## 13. 实现记录

### P1（2026-11-08）

已实现：迁移 `0008_scenes.sql`（`templates`、`scene_days`、`scenes`、`extractions`），四份内置模板加 `ambient`，拾贝切场景，串珠按模板抽取，「今日」页的只读时间线与场景卡片，以及 `GET /api/scenes`、`POST /api/scenes/rebuild`、`GET /api/templates`。

与原设计的差异：

- 模板定义写在 `src/server/scenes/templates.ts` 中（JSON 结构，带类型），读取时按 `(slug, version)` 幂等写入数据库。YAML 导出和 `_templates/` 目录放到 P5。
- 切场景先按长静默粗切（`SCENE_GAP_MS` = 3 分钟，块边界一定是场景边界），再按 `WINDOW_CHARS` = 6000 字分窗口。模型只返回每个场景第一句的序号，因此场景天然首尾相接、不重叠也不遗漏。窗口边界两侧模板相同的场景会合并回一个，窗口之间不设重叠区。
- 串珠单次抽取上限为 `EXTRACT_CHARS` = 12000 字。超长场景分段抽取后合并：列表拼接去重，单值取第一个非空。
- 失败语义：模型或账号不可用（`LLM_UNAVAILABLE`）时整天失败，并保留上一次的场景；单个场景抽取失败只记录在该场景上，当天仍标记为完成。服务重启后，遗留的 `running`/`queued` 状态显示为“上次整理因服务重启中断”。
- 过期判断：`scene_days.source_versions_json` 记录生成时每条录音的最新 transcript id，与当前值不一致就标记为过期，由用户点「重新整理」更新，不会静默覆盖。
- 转录成功后自动为录音所在的本地自然日排队，由 `scene_bots_enabled` 控制（默认 `1`，还没有设置界面）。场景任务属于联网任务，热点切换期间会被网络闸门暂停。
- 上面三个阈值都是暂定值，等 P0 实测后再调整。

验证：`tests/scenes.test.ts` 共 9 个用例。e2e 见 `.claude/skills/verify-openminutes/features/scenes-today.md`：无 Host 时验证空状态，Host 模式下用一段 18 秒的中文语音验证自动整理成功（1 次 ASR，2 次 `generateObject`）。
